# 同一套 Skill：加入 Jev 是否有额外收益？

日期：2026-09-27（Asia/Shanghai）。[脱敏记录与源码哈希](skill-ablation-validation.json)。

**此次两组各 2/2 通过，加入 Jev 没有减少 Astra 调用，也没有显示额外的成功率或速度收益。** 这是一个任务变体的四次真实运行，不能据此判断所有快速模型或所有桌面任务。

## 任务与对照

新场景 inventory_change_b：倒序排列字段，填写 Adapter、7、West；第一次 Review 出现通知，要求改为 North，再确认提交。它是已有配送变更任务的参数和布局变体，不是全新应用或工作流。

两组共用 Astra 提示、绑定格式、技能描述、参数验证、执行前观察及同一个多步 Skill 执行器。区别仅为是否在执行前让 Jev 从 use_skill / escalate 中选择。Astra 根据真实控件独立生成参数；日志确认四次运行的两份绑定完全一致。

每次使用新窗口，第一轮顺序为 Jev→直接，第二轮为直接→Jev。每次最多 3 次 Astra 规划，无自动重试。运行前后源码哈希一致。

## 成功证据与分工

四次均依次完成：提交初始表单技能 → Review 后遇通知暂停 → Astra 绑定 North → 确认通知并提交技能。独立回执均为 Adapter / 7 / North、passed=true；最终截图也核实为 North 和 PASS。

弹窗检测、暂停、逐步校验和恢复执行来自手写 Skill。Jev 本轮只决定是否执行 Astra 已绑定的技能，没有自主生成技能，也没有从多个不同技能计划中规划。因此本实验支持优先使用“Astra＋有校验的 Skill”作为这类已知工作流的基线；尚未证明这层 Jev 审核的必要性。后续若检验 Jev 的价值，应考察它是否能在共享计划下独立处理多个分支、实际替代后续 Astra 请求，而不是再确认 Astra 已作出的同一决定。
