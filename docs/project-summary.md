# ActStride 阶段总结

更新：2026-09-27。本文汇总截至 2026-09-26 的实现和实验；不把协议适配、模拟测试或未完成运行当作模型能力证明。

ActStride 探索用“快速决策模型 + 规划模型 + 可复用技能”减少 computer use 中的重复规划开销。参考 Jev-Mem 对高频决策与深度推理的分工思路，项目独立实现操作执行、状态检查和结果验证，没有复刻其记忆系统。

## 已实现

- **浏览器执行器**：11 个本地合成场景，允许截图和可见 DOM 控件信息，覆盖搜索、填表、工单分派、预约、通知设置及部分异常恢复。
- **参数化技能**：模型绑定任务参数，代码按步骤操作并检查状态，减少逐动作请求规划模型。技能由人工编写，尚不支持自动学习技能。
- **原生 Codex 桥接**：候选选择、宿主检查和官方 sky 桌面操作分阶段进行，已实现记事本新草稿技能。
- **独立 Windows UIA 后端**：读取可见控件，通过当前引用操作真实 Windows Forms 窗口；执行前检查状态，提交后由独立验证器判定。当前只允许操作项目自带的测试应用。
- **可替换快速模型**：OpenRouter Decisions 与本地 SystemOne 接口；桌面判断入口可以指定模型版本、阈值和重复次数，记录请求版本及实际返回版本。浏览器另有实验性图片输入通路，桌面判断仍固定使用 UIA 文本。
- **可复核记录**：保留失败、跳过、调用耗时、模型用量和源码哈希；付费请求预留费用，遇到未知费用停止后续消费。

## 实测说明了什么

### 1. 技能减少规划往返，是目前较明确的收益

[Windows 填表对照](windows-validation.md)共 12 次，三组各 4 次，全部通过：

| 路线 | 每任务规划请求 | 任务中位耗时 |
|---|---:|---:|
| 逐动作规划 | 5 次 | 150.9 秒 |
| 一次规划 + 技能执行 | 1 次 | 32.6 秒 |
| 一次规划 + Jev 确认 + 技能执行 | 1 次，另加一次 Jev | 32.6 秒 |

实际 UIA 操作数都为 5 次。双模型技能组相对逐动作组的四个配对快 3.92～4.64 倍，但与技能组相比，没有证明 Jev 额外确认带来收益。提速主要来自减少规划往返，不能全部归功于快速模型。

### 2. 快速模型直接替代判断，可以更快，但有正确率代价

[桌面判断实验](windows-judgment-validation.md)包括工单分流、供应商选择和退款条件判断。主要批次原计划 24 次，19 次完成，另有 1 次网络失败、4 次未运行：

| 路线 | 已完成判断正确率 | 包含技术失败的端到端成功 | 正确任务中位耗时 |
|---|---:|---:|---:|
| Astra | 10/10 | 10/10 | 32.07 秒 |
| Jev 优先 | 8/9 | 8/10 | 2.47 秒 |

两边均正确的 8 个配对中，Jev 路线快 9.20～38.58 倍。该比值不包含错误和网络失败，必须与完整成功率一起看。

关键失败是 Jev 以 0.83 的选择概率选了总价 30 美元的方案，正确方案为 27 美元。它没有触发 0.55 的转交阈值，说明高置信度不等于判断正确。此次没有实际触发低置信度转交，不能声称转交机制的效果已经得到真实验证。

另一个早期批次在 Astra 判断正确后遇到窗口状态变化，未执行点击；原因未确定，记录单独保留，没有并入主要批次的中位耗时。

### 3. 原生 Codex 桌面提速仍未得到证明

[记事本双模型试跑](native-dual-pilot.md)中，宿主单独执行成功；双模型组遇到快捷键没有新建标签页、反而写入字符的异常，随后停止。没有形成一对成功样本，因此不能报告提速比。独立 UIA 后端的结果不能迁移为官方 sky 模式的性能结论。

## 当前边界

实验主要使用固定的合成任务和少量重复。桌面是自带测试应用，浏览器允许读取 DOM；尚未证明任意第三方应用、纯截图、多应用长任务或通用成功率提升。

Astra 对照采用每次判断启动新 Codex CLI 进程的路线，耗时包含启动、网络与退出开销，不能当作模型纯推理速度比较。订阅额度与付费 API 分开记账，不把订阅调用标作免费。

Laya、Kev 和社区多模态接口目前是协议适配，尚未在本机运行模型权重。模型能够返回合法候选，不代表能够正确完成任务。最新版本适配的相关本地测试为 42/42 通过，使用模拟响应和本机 HTTP，没有新增真实模型推理。

## 接下来怎么继续

现阶段保留已验证的执行器、技能与测试集，等待更强的快速模型后，用相同题目和条件重新对照。接入入口已准备好，见[快速模型适配说明](fast-backends.md)。默认不会自动追随最新版本，也不会因一次较快结果自动扩大模型的操作范围。

评估优先看端到端成功率、正确任务耗时、错误类型和转交比例，而非只看价格或响应速度。后续值得单独验证代码计算与硬约束检查能否减少快速模型错误；这仍是待验证方向。

此前判断实验留下的未结算请求预留，已在 2026-09-27 的[其他快速模型测试](fast-chat-validation.md)前按提供方累计用量保守对账；该轮结束后未结算预留为 0。历史结果及失败记录继续保留，方便新版本作对照。
